# ADR-0016: Linear の Issue から develop へのマージまでを自動で進める

**Date**: 2026-11-24
**Status**: accepted
**Deciders**: HyuuNyackman

## Context

Linear の Issue を起点に、Claude による実装、テスト、PR の作成、マージまでを、人の操作なしに進めたい。
すでにあるのは、`@claude` のコメントで Claude が実装して PR を作る仕組みと、PR の自動レビュー ([ADR-0003](0003-claude-actions-guardrails.md)、[ADR-0004](0004-claude-actions-follow-repo-rules.md))、E2E (XCL-87)、pgTAP (XCL-88) である。
一方で、レビューはコメントを書くだけでマージを止められず、起動に人の `@claude` が要り、CI が落ちても止まる。
本番への反映は `main` に限定した ([ADR-0015](0015-production-deploy-only-from-main.md))ので、`develop` へのマージは自動にできる。

## Decision

- **起動**: Linear の Issue に、ラベル `agent-ready` を付ける。GitHub の Issue に同期されたとき、ラベルを付けたのがリポジトリのオーナーなら、Claude が実装を始める。
- **CI のゲート**: check (lint・typecheck・format)、E2E、pgTAP、Claude のレビューを必須にする。ユニットテストは、導入後に加える。
- **レビューのゲート化**: レビューの結果を、PR のチェックにする。判定は、レビューが PR に投稿するコメントで行う。「No issues found」を含むときだけ成功とし、それ以外と、コメントが見つからないときは失敗とする。
- **再レビュー**: 修正の push のたびに、レビューを実行する (ADR-0003 の「`synchronize` では実行しない」を変更する)。必須チェックは、最新のコミットに対する結果が要るため。
- **自動修正**: CI の失敗やレビューの指摘で、Claude が同じブランチに修正を push する。上限は 3 回で、超えたら人に渡す。
- **マージ**: 必須チェックがすべて通った `develop` 向けの PR は、自動で squash マージする。必須のレビュー人数は 0 にする (一人運用で、自分の PR は承認できないため)。`main` へは自動でマージせず、人が `develop → main` の PR で確認する。
  - 自動マージの対象は、Claude が作る `claude/` ブランチの、`develop` 向けの PR だけ。
  - `develop` の必須チェックは、管理者が迂回できるようにする。ワークフローのファイルを変更する PR は、claude-code-action の仕様で Claude のレビューがスキップされ、チェックが赤くなる。その場合に、オーナーが内容を確認して、マージするための逃げ道。
  - `main` は、管理者にも必須チェックを強制する。承認人数は 0 にして、リリース PR を自分でマージできるようにする。
  - ブランチ保護の設定は `scripts/ci/apply-branch-protection.sh` に置き、手元で適用する。
- **E2E の範囲**: Web のみ。ネイティブの E2E (Maestro) は、ネイティブ版を出すときに再検討する (XCL-69)。

## Alternatives Considered

### Alternative 1: Linear のステータス変更で起動する

- **Pros**: 普段のステータス操作だけで起動できる。
- **Cons**: GitHub 側には、開閉以外のステータス変更が同期されない。Linear の Webhook を受ける中継 (Cloudflare Worker など) と、`repository_dispatch` が要る。Linear の GitHub 連携も、PR の作成やマージでステータスを動かすため、意図しない起動が起きやすい。
- **Why not**: 追加の仕組みと誤爆の心配に見合わない。ラベルなら、GitHub 側で直接検知でき、付けたのがオーナーかも確認できる。

### Alternative 2: 変更のリスクをパスで判定し、低リスクだけ自動マージする

- **Pros**: マイグレーションなど、危険な変更を人が必ず見られる。
- **Cons**: 判定の仕組みと、例外の管理が要る。
- **Why not**: 本番への反映を `main` に限定したので、`develop` への自動マージは本番に影響しない。人の確認を `develop → main` に集めるほうが単純。

### Alternative 3: `main` まで自動でマージする

- **Pros**: 人の操作が完全になくなる。
- **Cons**: 本番に出る変更を、人が一度も確認しない。
- **Why not**: 本番への反映は、人が確認する 1 回を残す。

### Alternative 4: レビューの判定を、構造化した出力 (JSON スキーマ) で受ける

- **Pros**: コメントの文言に依存しない。
- **Cons**: 使っている code-review プラグインのコメント形式が、文書化されていない。スキーマ出力との併用で、コメントの投稿に影響が出るかが分からない。
- **Why not**: まず、実際に出る文言で判定する。文言が変わって運用が不便なら、置き換える。

## Consequences

### Positive

- ラベル 1 つで、実装から `develop` へのマージまでが進む。
- 人の確認は、`develop → main` の PR に集まる。

### Negative

- 修正のたびにレビューが走るので、利用枠の消費が増える。
- 判定が文言に依存する。

### Risks

- **Issue の本文は、Claude への入力になる。** Linear に書けるのが自分だけで、起動はオーナーが付けたラベルだけ、という前提で成り立つ。外部の人が書ける経路が増えるなら、自動マージをやめる。
- **レビューの判定は、「No issues found」という文言に依存する。** 文言が変わると、すべての PR のチェックが失敗する (安全側に倒れる)。その場合は、判定の文言を直す。誤検知でマージが止まった場合は、人が確認して対応する。
- **Claude が作った PR が、CI を起動するか。** GitHub のトークンの種類によっては、起動しない。XCL-90 で実機で確認する。
- **利用枠。** ターン数と修正の回数は、リポジトリ変数で調整できるようにする。
- **ユニットテストが、まだない。** 画面のロジックの回帰は、E2E の範囲でしか検出できない (XCL-86)。
- **ブランチ保護の設定の誤りで、必須チェックが効かなくなる。** 設定は XCL-93 で行い、実際に失敗した PR がマージされないことを確かめる。
