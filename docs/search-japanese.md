# 検索 (pg_trgm) と日本語の精度

XCL-67 で、投稿本文とユーザー (handle・表示名) の検索を、Postgres の `pg_trgm` で作った。RPC は `search_posts` と `search_users` (どちらもログイン済みだけが呼べる)。

## 仕組み

- 検索は `ilike '%語%'` (大文字小文字を区別しない部分一致)。`posts.body`、`profiles.handle`、`profiles.display_name` に `gin_trgm_ops` の GIN インデックスを張り、`ilike` を速くする。
- 検索語の `%` `_` `\` は文字として扱う (エスケープする)。
- 全文検索 (`tsvector`) は使わない。Postgres 標準の辞書には日本語の形態素解析がなく、単語に分けられないため。

## 日本語での限界

- trigram は 3 文字の並びで索引する。**1〜2 文字の検索語**では、索引から候補を絞れず、全件を順に調べる (結果は正しいが遅くなる)。日本語は 1〜2 文字の語が多いので、データが増えると影響が出る。
- pg_trgm は、文字が英数字かをデータベースのロケールで判定する。ロケールが `C` のように日本語を英数字と見なさない設定だと、日本語の文字は trigram にならず、索引が効かない (結果は正しいが、全件を調べる)。Supabase の既定のロケールで日本語に索引が効くかは、実機で `explain` を取って確かめていない。
- 部分一致なので、表記ゆれ (ひらがな・カタカナ、全角・半角、「サーバー」と「サーバ」) は同じ語として扱われない。形態素解析による分かち書きや、類義語の対応はできない。
- ランキングはしない。投稿は新しい順、ユーザーは handle の前方一致を先にして handle 順。

## 将来の選択肢

- 規模が大きくなったら、`pgroonga` (Supabase で使える日本語対応の全文検索) や外部の検索基盤を比べる。
- 表記ゆれは、保存時に正規化した列 (NFKC、かな統一) を足して、そこを検索する方法がある。
